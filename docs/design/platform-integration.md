# 平台集成与后续演进合同

> 2026-11-11 重规划。本文区分当前实现与待实施合同；不新增 API、状态字段或部署承诺。跨仓排期、工作量和关闭证据唯一登记在主仓[规划总账](../../../zhuzhao/docs/review/planning-backlog.md)，本仓按编号承接，不再维护另一套估算。通用约束见主仓[工程公约](../../../zhuzhao/docs/standards.md)。

## 1. 定位与能力供给

taskrunner 负责本平台任务的受理、计划触发、投递、尝试记录、重试与恢复。安全业务规则、资源授权、工单/风险状态由能力属主持有。taskrunner 不是领域事件总线、用户权限系统或通用 SOAR。

企业 SOC/SIEM、SOAR、CMDB、威胁情报、Agent/知识平台已确认存在，具体接口和授权合同待验证。专业检测/关联、资产权威、情报生产、取证封禁、复杂专业编排继续由相应平台提供；本服务只承担必要调度、受控调用和执行事实关联。旧“自建通用 DAG、全量迁回 SOAR、完整脚本平台”的设想不再作为默认交付。

智能体采用两轨：对接已有企业 Agent；支持基于本平台特有工具的领域 Agent 最小受控 host。host 的模型、工具选择、预算与确认归平台智能模块，计划调度仍复用 taskrunner，不新增 AI 调度器。模型只通过已有内网模型或允许环境的外部 API 调用，不规划训练、部署或 GPU 基础设施。

## 2. 当前数据与状态写主

- taskrunner 的 `jobs`、`job_runs`、受理/入队标记和执行尝试由本服务写入；Redis/Asynq 是可恢复投递面，不替代数据库事实。`Service.Submit` 采用 DB-first；详见[运行设计](taskrunner.md)和[备份恢复](../ops/backup.md)。
- 业务能力的输入校验、副作用、业务终态和业务结果由能力属主写入。主仓保存调用凭证与业务审计，两仓用 task/request 标识关联，不跨库写表，不宣称跨服务事务。
- 当前 `Deps.handleCallback` 为每次投递产生 execution_id，`Store.MarkRunning` / `Finish` 按状态、attempt 与 execution_id 限定写者。这保护执行库收尾身份，不证明业务已经完成，也不保证外部副作用只执行一次。
- 当前回调地址由服务配置固定，用户不能提交 `callback_url`。`dept` 是标签、`submitted_by` 是归因/筛选，不是用户或组织隔离策略。准确路由和字段见[HTTP 与回调契约](../api/contract.md)。

源码锚点：`internal/service/submit.go` 的 `Service.Submit`、`internal/service/cron.go` 的 `Loop.FireDue`、`internal/worker/worker.go` 的 `Deps.handleCallback`、`internal/repository/store.go` 的 `MarkRunning` / `Finish`。

## 3. C03：完成语义，P6.0 必须先收口

当前短动作契约要求业务完全成功后回 2xx；但主仓 `JobsCallbackService.Execute` 的在途重复回调分支可以返回 2xx，而本仓 `callback.Client.Do` 将 2xx 作为成功，worker 随后写 succeeded。静态调用链说明存在“业务仍在途、执行侧提前成功”的路径，不能以 execution_id 栅栏或 HTTP 成功掩盖此差异；本页没有运行复现或修复。

**C03 / P6.0** 联合修正并冻结以下合同：

1. 区分已受理、仍在执行、业务已完成、部分成功、结果未知；短同步动作不能把在途受理当最终成功。
2. 长任务用持久调用标识及受权查询/完成通知衔接，不能把异步受理状态码直接判为 succeeded。业务终态、投递状态与通知送达分别记录。
3. 明确响应丢失、执行成功但记账失败、陈旧写者和对账恢复的处理；新旧调用方按兼容窗口共同升级，不单边改状态码。
4. 副作用由能力属主按稳定幂等键和输入快照保护；同键不同输入、重复在途、已完成重放各有明确响应。签名时间窗不是业务幂等。
5. 先补计划发生次的稳定时隙键与领取/推进保护，避免多调度器、推进失败或重启为同一时刻创建多个随机 task_id；P7 的 I03 在此基础上扩展调度政策，不能把基础防重推迟到自然语言计划任务上线之后。

出口是跨仓正反例与适用门禁验证，不是仅改响应文案。未关闭前不得扩大依赖“成功即推进业务”的自动化或 AI 写操作。

## 4. D12：结果、恢复与取消，P6.3 承接

当前 reclaim 自动补投范围、running 的人工处置、Redis archived 依赖与仅取消未开始任务的限制以[恢复](../ops/backup.md)和[当前 API](../api/contract.md)为准。数据库暂时不能认领时 worker 的容忍分支、终态落库失败主要记日志、终败通知尽力发送，都不能当作高风险动作的可靠完成证明。

**D12 / P6.3** 以前述 C03、主仓 R01/P6.1 可靠业务交接和已发布定义版本为前置，建立相互配套的数据面：结果摘要与大结果/日志/工件引用、尝试历史、错误类别、未知结果/待对账入口、受权取回、积压和 stuck 观测。状态/字段名称在实施合同确定，本页不虚构当前已有接口。

取消请求与取消已生效分开；HTTP context 取消不能撤回已发生的副作用。重试投递、重新执行业务、新建重放及人工恢复有明确名称与权限。外部执行成功但本地记账失败、重启在途和通知失败都必须保留可操作恢复路径。

参数、队列载荷、结果、日志和备份分别定留存；清理不能破坏 task_id 幂等承诺，应保留最小去重凭证或明确新的幂等窗口。凭据按引用传入，敏感值不进入模型请求、普通运行列表和日志。

## 5. I01/I02/I03：能力、身份和计划调度，P7 承接

**I01 能力合同**：主仓持有业务 Action/Query 的稳定 ID、版本、输入输出、权限和风险策略；taskrunner 持有执行路由投影、受理与尝试事实。现有 handler 注册表和工单 post-action 各保留内部语义，通过 adapter 接合同，不直接强合。动态目录尚未实现，旧[能力目录方案](capability-registry.md)只作重规划输入。地址注册/更新必须由受权服务完成并校验目标；不恢复用户任意回调 URL。

**I02 身份与授权**：用户可调用范围、运行可见性、敏感参数、取消/重试资格由主仓统一门面执行。服务 AK/SK 验证调用方，X-Operator 只提供可信归因，不等于委托已获准；自然语言、MCP、领域 host 与 UI 走相同业务授权。持续任务保存受限 grant，不长期复用浏览器 JWT；账号停用、撤权后的暂停与接管要可验证。

**I03 调度政策**：继承 C03 在 P6.0 修正的完成/时隙合同，完善定义版本、租约、取消、预算、追踪与状态投影。实施前明确时区、错过执行、同计划并发、截止时间、禁用与已排队任务、人工立即执行规则。固定基线 cron 尚无完整发生次保护，修复前按单调度主运行；task_id 去重不能代替计划发生次去重。

I01/I02/I03 的先决合同在 P7 开工前收口，自然语言创建周期任务必须在调度幂等和持续授权通过后上线。共用工作只在主总账估算一次。

P6.3 的 A02 仅限真人当次交互确认建单，使用当前用户身份、实时业务授权与 R01 幂等交接，不以 P7 持续 grant 为前置；P7 的 A04 自然语言计划任务和无人值守动作必须等待 I02/I03，不能把一次确认扩大为永久委托。

## 6. R03/R04：胶水执行和专业平台协同，P8 承接

**R03** 先核现有 SOAR/专业执行接口能否覆盖本平台胶水场景。确有不可覆盖的脚本与隔离缺口，再比较成熟 runner 或最小受控执行端；不默认建设完整脚本库、制品市场或通用编排引擎。采用新执行端时冻结 dispatch/report、租约/栅栏、结果引用、取消、版本和凭据合同，worker 不拥有工单/风险业务判定。

**R04** 对已有 SOAR、企业 Agent 和知识 API 做受控调用，记录外部 run/结果引用、权威状态、超时/取消与未知效果。每条链只有一个编排主和一个重试主；领域 Agent 的有限 tool loop 不和 TR/SOAR同时续链。专业流程编辑可深链到属主系统，本平台保留安全责任与证据。

R03 在 P8 开工前给“复用外部/成熟组件/最小补建/退出”结论；R04 交付接入与对账合同。真实 API 暂不可用时先保留 mock/contract，不据此重造专业平台。

## 7. 验收与变更纪律

长期保留大量合成 mock：固定时钟、重复触发、回调在途/完成/未知、HTTP 错误、DB/Redis 故障、陈旧 report、取消竞争、预算耗尽、撤权与部分成功。mock 不绕过真实授权、状态机与幂等。

验收分三层单独留证：离线 mock 验证场景和故障分支；contract 验证调用、schema、签名/身份和兼容；real 验证实际专业服务、部署网络、配额、取消与业务效果。前两层可以先完成，不能代替真实接入收据；现有真实集成与生态 acceptance 保留。

本轮仅规划落档，C03/D12/I01–I03/R03/R04 均未因本文关闭。实施时同步本仓 API、运行/恢复文档与主总账；新增状态/字段/协议先写兼容和回滚，再修改代码并运行适用门禁。

## 按任务配置错失策略（同日问答候选）

创建/编辑计划选择skip、coalesce_latest或catch_up_bounded，不能所有任务固定补一次。正常轮询迟到由grace区分；回补年龄/总量、每批数量、并发/速率和超限余项分别有界。逐时隙回补传原scheduled_for/业务时区/数据区间及明确生效参数版本；无历史数据不冒充补旧日报。仅补未物化时隙，已有failed/unknown走原ID重试/对账；策略/停启切换有barrier与旧时隙映射，不因加revision重复效果。详细权威见主仓[跨仓合同](../../../zhuzhao/docs/design/cross-repo-execution-contract.md)C03。owner提出按任务配置方向，具体默认/预算仍候选；未改API/schema/调度源码。
