# 能力目录：已批准、尚未实施

2026-10-29 所有者已批准将能力目录整体提入 Phase 6；当前没有 `capability_registry` 表、自注册 API 或执行端 SDK。当前提交和任务定义仍由服务配置指定唯一回调目标，调用方不能传入地址。

批准范围为三步同批：建立能力目录与启动自注册、提交/cron 解析并记录路由快照、处理存量定义；执行端通用 SDK 同批放入 zhuzhao-utils。领域表和流程归本仓，utils 不持业务数据库。

## 方案要点

每个能力一条扁平 code，引用服务身份 `owner_ak`；同 AK 可幂等更新、跨 AK 抢注拒绝。目录存 taskrunner 自有 DB，自注册与管理/配置兜底并存，不引入 etcd/Consul，不做 TTL/心跳。提交时记录解析结果，cron 每次触发重新解析；执行端内部注册表再将 action 分发给 handler。

## 实施前需要收敛的约束

早期方案保留“显式 callback_url 覆盖”，现行 W0b 为 SSRF 防线已经拒绝用户地址。文档整理不重新授权覆盖口子。实施批必须把目录注册的权限、目标校验与既有固定地址约束一起评审，并说明升级/回滚兼容。新命名 `action_code` 与现有一次性提交 `action`、任务定义 `action_id` 的迁移也在该批处理。

原批准过程、五项决议、已取消的触发闸门与旧三步草图见 [原设计快照](../review/archive/taskrunner-design-history.md)。历史约 3–4 人日只是当时估算；实施时据安全约束重估。
