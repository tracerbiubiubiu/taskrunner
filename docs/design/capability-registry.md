# 能力目录：历史方案与重规划承接

> **2026-11-11 当前口径**：本页保留历史批准方案，作为重规划输入；不再单独作为当前排期或唯一目录归属合同。业务能力合同、执行路由与身份分别由[平台集成合同](platform-integration.md)的 I01/I02/I03 承接，排期与关闭证据归主仓[规划总账](../../../zhuzhao/docs/review/planning-backlog.md)。旧“Phase6三步同批/SDK必建”不覆盖新路线。

2026-10-29 所有者曾批准将能力目录整体提入 Phase 6；当前没有 `capability_registry` 表、自注册 API 或执行端 SDK。当前提交和任务定义仍由服务配置指定唯一回调目标，调用方不能传入地址。

## 历史批准范围（复核输入）

当时批准范围为三步同批：建立能力目录与启动自注册、提交/cron 解析并记录路由快照、处理存量定义；曾设想执行端通用 SDK 同批放入 zhuzhao-utils。下述数据库和元数据归属是该时点方案，当前应区分主仓业务目录与本仓执行路由投影；utils 仍不持业务数据库。

## 方案要点

每个能力一条扁平 code，引用服务身份 `owner_ak`；同 AK 可幂等更新、跨 AK 抢注拒绝。目录存 taskrunner 自有 DB，自注册与管理/配置兜底并存，不引入 etcd/Consul，不做 TTL/心跳。提交时记录解析结果，cron 每次触发重新解析；执行端内部注册表再将 action 分发给 handler。

## 实施前需要收敛的约束

早期方案保留“显式 callback_url 覆盖”，现行 W0b 为 SSRF 防线已经拒绝用户地址。文档整理不重新授权覆盖口子。实施批必须把目录注册的权限、目标校验与既有固定地址约束一起评审，并说明升级/回滚兼容。新命名 `action_code` 与现有一次性提交 `action`、任务定义 `action_id` 的迁移也在该批处理。

`ActionMeta` 元数据归属仍需实施前确认：由自注册报文携带元数据并扩展目录列，或继续保留在各执行端读面。它关系到任务控制台依赖 `params_schema` 的动态表单，当前没有据此选定某一种目录合同；两案出处为[原设计快照](../review/archive/taskrunner-design-history.md)的2026-10-29修订行。本轮补齐待定项登记，不选择两案或实施能力目录。
